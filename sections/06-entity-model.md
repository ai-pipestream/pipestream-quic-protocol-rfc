# Section 6: Entity Model

## 6. Entity Model

This section defines the entity model for PipeStream, specifying the structure and semantics of documents flowing through the distributed processing pipeline. The entity model provides a flexible, layered approach to document representation that supports diverse processing requirements.

### 6.1. Core Fields

Every PipeStream entity is represented as a PipeDoc message. The following table defines the core fields that MUST be present or MAY be populated for each entity.

#### 6.1.1. Entity Identification

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| doc_id | string | REQUIRED | Unique identifier for this document across the entire system. MUST be deterministically derived as hash(datasource_id + source_doc_id). Implementations SHOULD use UUID format for generated identifiers. |
| ownership | OwnershipContext | OPTIONAL | Tracks which account and datasource created or owns this document. |
| doc_id_derivation | DocIdDerivation | OPTIONAL | Records how the doc_id was determined for auditability, debugging, and understanding idempotency semantics. |

The doc_id field serves as the primary key for entity identification. Implementations MUST ensure that doc_id values are unique within the scope of a single PipeStream deployment. The derivation method SHOULD be recorded in doc_id_derivation to support debugging and audit requirements.

The DocIdDerivationMethod enumeration defines the following derivation strategies:

| Value | Description |
|-------|-------------|
| DOC_ID_DERIVATION_METHOD_UNSPECIFIED | Derivation method not specified. |
| DOC_ID_DERIVATION_METHOD_CLIENT_PROVIDED | doc_id was already set by the client in PipeDoc. |
| DOC_ID_DERIVATION_METHOD_SOURCE_DOC_ID | doc_id derived from intake request source_doc_id. |
| DOC_ID_DERIVATION_METHOD_SOURCE_URI | doc_id derived from PipeDoc.search_metadata.source_uri (canonicalized). |
| DOC_ID_DERIVATION_METHOD_SOURCE_PATH | doc_id derived from PipeDoc.search_metadata.source_path (normalized). |
| DOC_ID_DERIVATION_METHOD_SERVER_GENERATED | doc_id was generated by the server (explicit opt-in only). |

#### 6.1.2. Search Metadata

The SearchMetadata message contains standardized fields for search engine indexing and querying. Implementations SHOULD populate these fields to enable out-of-the-box search functionality.

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| title | string | OPTIONAL | Document title or heading. Human-readable name for the entity. |
| body | string | OPTIONAL | Full text content of the document. |
| keywords | Keywords | OPTIONAL | Extracted keywords for search and categorization. Contains a repeated list of keyword strings. |
| document_type | string | OPTIONAL | Document type classification (e.g., "PDF", "HTML", "DOCX"). |
| source_uri | string | OPTIONAL | Original source URI where the document was obtained. |
| source_mime_type | string | OPTIONAL | MIME type of the source document. |
| creation_date | Timestamp | OPTIONAL | Timestamp when the document was originally created. |
| last_modified_date | Timestamp | OPTIONAL | Timestamp when the document was last modified at source. |
| processed_date | Timestamp | OPTIONAL | Timestamp when the document was processed by the pipeline. |
| language | string | OPTIONAL | Language code of the document content (e.g., "en", "es", "fr"). Implementations SHOULD use ISO 639-1 codes. |
| author | string | OPTIONAL | Document author or creator. |
| category | string | OPTIONAL | Category or classification label for the document. |
| tags | Tags | OPTIONAL | Key-value tags for flexible categorization. |
| content_length | int32 | OPTIONAL | Length of the document content in bytes or characters. |
| relevance_score | double | OPTIONAL | Relevance score for search ranking purposes. |
| custom_fields | Struct | OPTIONAL | Additional custom fields not covered by standard schema. |
| metadata | map<string, string> | OPTIONAL | Generic key-value metadata for extensibility. |
| doi | string | OPTIONAL | Digital Object Identifier for academic papers and publications. |
| source_path | string | OPTIONAL | Path portion of source_uri for categorization. |
| source_path_segments | repeated string | OPTIONAL | Split path segments from source_path. |
| source_slug | string | OPTIONAL | Last segment of source_path. |

#### 6.1.3. Document Structure

The DocOutline message provides format-neutral document outline representation for navigation and structural understanding.

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| sections | repeated Section | REQUIRED | Sections in preorder traversal order. |

Each Section within a DocOutline contains:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| id | string | OPTIONAL | Stable identifier if present in source document. |
| title | string | OPTIONAL | Section title or heading text. |
| depth | int32 | REQUIRED | Nesting depth where 0 is top level. |
| heading_level | int32 | REQUIRED | Heading level (HTML h1=1, Markdown #=1, 0 if unknown). |
| href | string | OPTIONAL | Relative link or fragment identifier if applicable. |
| parent_id | string | OPTIONAL | Parent section identifier for hierarchical navigation. Used for vaporized parts referencing their parent entity. |
| order_index | int32 | REQUIRED | Preorder position index within the document. |
| tags | repeated string | OPTIONAL | Classification tags (e.g., "chapter", "appendix", "figure", "table", "nav"). |
| font_size_rel | float | OPTIONAL | Relative font size (0.0-1.0) if inferred from styling. |
| page_start | int32 | OPTIONAL | Starting page number if known (PDF/EPUB). |
| page_end | int32 | OPTIONAL | Ending page number if known (PDF/EPUB). |

#### 6.1.4. Link References

The discovered_links field contains LinkReference messages representing links discovered within the document.

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| url | string | REQUIRED | Href or absolute URL when resolvable. |
| text | string | OPTIONAL | Anchor text or link label. |
| rel | string | OPTIONAL | rel attribute if present (e.g., "nofollow", "canonical"). |
| type | string | OPTIONAL | MIME type attribute or inferred type. |
| is_external | bool | OPTIONAL | Whether the link points to a different host than source_uri. |

#### 6.1.5. Ownership Context

The OwnershipContext message tracks ownership for security, auditing, and access control.

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| account_id | string | REQUIRED | Account that owns this document. |
| datasource_id | string | REQUIRED | DataSource (account + connector type binding) that produced this document. Deterministic: hash(account_id + connector_id). |
| connector_id | string | OPTIONAL | Connector type that created this document (e.g., "object-store", "file-crawler"). |

### 6.2. Four Layers

The PipeStream entity model supports four distinct data layers. A single entity MAY have multiple layers populated simultaneously. Each layer serves a specific purpose in the document processing lifecycle.

```
+------------------------------------------------------------------+
|                          PipeDoc                                 |
|  +------------------------------------------------------------+  |
|  |  Layer 0: BlobBag (Raw Binary Data)                        |  |
|  |  - Original document bytes                                  |  |
|  |  - Images, attachments, embedded files                      |  |
|  +------------------------------------------------------------+  |
|  +------------------------------------------------------------+  |
|  |  Layer 1: SemanticLayer (Semantic Chunks)                  |  |
|  |  - SemanticProcessingResult with SemanticChunks            |  |
|  |  - Text segments with vector embeddings                     |  |
|  +------------------------------------------------------------+  |
|  +------------------------------------------------------------+  |
|  |  Layer 2: ParsedData (Structured Extraction)               |  |
|  |  - ParsedMetadata from various parsers                      |  |
|  |  - JSON/key-value representation                            |  |
|  +------------------------------------------------------------+  |
|  +------------------------------------------------------------+  |
|  |  Layer 3: CustomEntity (Extension Point)                   |  |
|  |  - structured_data as google.protobuf.Any                  |  |
|  |  - Domain-specific protobuf payloads                        |  |
|  +------------------------------------------------------------+  |
+------------------------------------------------------------------+
```

#### 6.2.1. Layer 0: BlobBag (Raw Binary Data)

The BlobBag layer provides storage for raw binary data associated with an entity. This layer is designed for original document bytes, images, attachments, and any other binary content that requires parsing or processing.

##### 6.2.1.1. BlobBag Structure

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| blob | Blob | CONDITIONAL | Single blob content. Mutually exclusive with blobs. |
| blobs | Blobs | CONDITIONAL | Multiple blob contents. Mutually exclusive with blob. |

Implementations MUST populate exactly one of blob or blobs within a BlobBag. The choice between single and multiple blob storage SHOULD be based on the document structure being represented.

##### 6.2.1.2. Blob Structure

Each Blob within a BlobBag contains:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| blob_id | string | REQUIRED | Unique identifier for this blob. |
| drive_id | string | REQUIRED | Drive/bucket identifier where this blob belongs. |
| data | bytes | CONDITIONAL | Inline binary data for small files or sensitive content. Mutually exclusive with storage_ref. |
| storage_ref | FileStorageReference | CONDITIONAL | Reference to external object storage for large files. Mutually exclusive with data. |
| mime_type | string | OPTIONAL | MIME type of the blob content. |
| filename | string | OPTIONAL | Original filename if available. |
| encoding | string | OPTIONAL | Character encoding for text-based blobs. |
| size_bytes | int64 | REQUIRED | Size of the blob content in bytes. |
| checksum | string | OPTIONAL | Checksum value for integrity verification. |
| checksum_type | ChecksumType | REQUIRED | Type of checksum algorithm used. |
| metadata | Struct | OPTIONAL | Additional blob metadata stored in the database. |

##### 6.2.1.3. Storage Reference

For blobs stored externally, the FileStorageReference message provides:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| drive_name | string | REQUIRED | Drive name mapping to the remote storage bucket. |
| object_key | string | REQUIRED | Object path/key within the bucket. |
| version_id | string | OPTIONAL | Object version ID if versioning is enabled. |

##### 6.2.1.4. Checksum Types

Implementations MUST support the following checksum algorithms:

| Value | Description |
|-------|-------------|
| CHECKSUM_TYPE_UNSPECIFIED | Unspecified checksum type. |
| CHECKSUM_TYPE_MD5 | MD5 checksum (128-bit). |
| CHECKSUM_TYPE_SHA1 | SHA-1 checksum (160-bit). |
| CHECKSUM_TYPE_SHA256 | SHA-256 checksum (256-bit). RECOMMENDED for new implementations. |
| CHECKSUM_TYPE_SHA512 | SHA-512 checksum (512-bit). |

Implementations SHOULD use CHECKSUM_TYPE_SHA256 for new blob storage operations.

##### 6.2.1.5. Use Cases

The BlobBag layer is designed for:

- Storage of original document bytes (PDF, DOCX, etc.)
- Image content requiring OCR or visual analysis
- Attachment and embedded file storage
- Multi-part document assembly
- Binary content that requires downstream parsing

#### 6.2.2. Layer 1: SemanticLayer (Structured Semantic Chunks)

The SemanticLayer provides structured semantic chunking and vector embedding capabilities. This layer enables vector search, semantic similarity matching, and retrieval-augmented generation (RAG) workflows.

##### 6.2.2.1. SemanticProcessingResult Structure

Semantic processing results are stored in the semantic_results field of SearchMetadata:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| result_id | string | REQUIRED | Unique identifier for this result set. |
| source_field_name | string | REQUIRED | Name of the PipeDoc field that was processed (e.g., "body", "title", "abstract"). |
| chunk_config_id | string | REQUIRED | Identifier for the chunking configuration used (e.g., "sentence_splitter_v1", "token_chunker_512_overlap_50"). |
| embedding_config_id | string | REQUIRED | Identifier for the embedding model/configuration used (e.g., "ada_002_v1", "minilm_l6_v1"). |
| result_set_name | string | OPTIONAL | Generated name for this result set. Used as field name prefix in search indexes. |
| chunks | repeated SemanticChunk | REQUIRED | List of semantic chunks with embeddings from this configuration. |
| metadata | map<string, Value> | OPTIONAL | Processing run metadata (e.g., model version, execution time). |

##### 6.2.2.2. SemanticChunk Structure

Each SemanticChunk contains:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| chunk_id | string | REQUIRED | Unique identifier for this chunk within its parent result. |
| chunk_number | int64 | REQUIRED | Sequential number of this chunk within its parent result. |
| embedding_info | ChunkEmbedding | REQUIRED | Text and embedding information for this chunk. |
| metadata | map<string, Value> | OPTIONAL | Chunk-specific metadata (e.g., page number, section). |

##### 6.2.2.3. ChunkEmbedding Structure

The ChunkEmbedding message contains the actual text content and vector embedding:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| text_content | string | REQUIRED | Actual text content of the chunk. |
| vector | repeated float | REQUIRED | Vector embedding for this chunk's text. |
| chunk_id | string | OPTIONAL | Unique identifier for this chunk. |
| original_char_start_offset | int32 | OPTIONAL | Character offset where chunk starts in original document. |
| original_char_end_offset | int32 | OPTIONAL | Character offset where chunk ends in original document. |
| chunk_group_id | string | OPTIONAL | Identifier for a group of related chunks. |
| chunk_config_id | string | OPTIONAL | Identifier for the chunking configuration used. |

##### 6.2.2.4. Embedding Structure

For document-level or non-chunk embeddings:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| model_id | string | OPTIONAL | Model identifier that generated this embedding. |
| vector | repeated float | REQUIRED | Vector representation as floating-point values. |

##### 6.2.2.5. Use Cases

The SemanticLayer is designed for:

- Vector similarity search across document collections
- Semantic similarity matching between documents or queries
- Retrieval-augmented generation (RAG) pipelines
- Multi-model embedding support (different embedding models for different use cases)
- Chunk-level retrieval with offset tracking for source attribution

#### 6.2.3. Layer 2: ParsedData (Extracted Structured Data)

The ParsedData layer stores structured data extracted by document parsers. This layer supports multiple parsers operating on the same document, with results stored under parser-specific keys.

##### 6.2.3.1. ParsedMetadata Structure

Parsed data is stored in the parsed_metadata map field of PipeDoc:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| parser_name | string | REQUIRED | Name of the parser that produced this data (e.g., "tika", "docling"). |
| parser_version | string | REQUIRED | Version of the parser (e.g., "4.0.0", "1.2.3"). |
| parsed_at | Timestamp | REQUIRED | Timestamp when parsing occurred. |
| data | Any | REQUIRED | Parser-specific output data as google.protobuf.Any. |

##### 6.2.3.2. Semantic Rules

The parsed_metadata field operates under the following semantic rules:

1. The field is append-only: parsers MAY add new entries but MUST NOT modify or delete existing entries.
2. Keys are parser-specific identifiers (e.g., "tika", "docling").
3. The data field contains parser-specific protobuf messages serialized as google.protobuf.Any.
4. Types registered in the schema registry with JARs in the classpath will deserialize to their actual type.
5. Unknown types fall back to dynamic messages.

##### 6.2.3.3. Use Cases

The ParsedData layer is designed for:

- Metadata extraction from binary documents (PDF, DOCX, etc.)
- Schema mapping and data normalization
- Parser-specific output preservation
- Multi-parser workflows with incremental enrichment
- Audit trails for parsing operations

#### 6.2.4. Layer 3: CustomEntity (Extension Point)

The CustomEntity layer provides an extension point for domain-specific data that does not fit into the standard entity model. This layer enables arbitrary protobuf payloads to be attached to entities.

##### 6.2.4.1. structured_data Field

The structured_data field in PipeDoc uses google.protobuf.Any for extensibility:

| Field | Type | Requirement | Description |
|-------|------|-------------|-------------|
| type_url | string | REQUIRED | A URL/resource name that uniquely identifies the type of the serialized protocol buffer message. |
| value | bytes | REQUIRED | The serialized protocol buffer message data. |

The type_url field MUST follow the format specified in google.protobuf.Any:

```
type.googleapis.com/packagename.messagename
```

##### 6.2.4.2. Type Resolution

Implementations MUST support the following type resolution behavior:

1. Types registered in the schema registry with corresponding JARs in the classpath MUST deserialize to their actual protobuf type.
2. Unknown types MUST fall back to dynamic message handling.
3. All data in structured_data SHOULD be indexed into the search engine unless configured otherwise.

##### 6.2.4.3. Use Cases

The CustomEntity layer is designed for:

- Domain-specific data models (e.g., e-commerce products, medical records)
- Custom schema extensions without modifying core protocol
- Integration with external systems requiring specific data formats
- Experimental features and prototyping

### 6.3. Protobuf Encoding

All PipeStream entities MUST be encoded using Protocol Buffers version 3 (proto3) syntax. This section specifies the encoding requirements and wire format conventions.

#### 6.3.1. Wire Format Requirements

1. Entities MUST be serialized using the standard Protocol Buffers binary wire format as specified in the Protocol Buffers Language Guide.

2. Implementations MUST use proto3 syntax conventions:
   - All fields are optional by default (no required keyword)
   - Default values are not serialized on the wire
   - Unknown fields MUST be preserved during parsing

3. Field numbering MUST follow proto3 conventions:
   - Field numbers 1-15 require one byte for encoding (use for frequently occurring fields)
   - Field numbers 16-2047 require two bytes
   - Field numbers MUST NOT change once assigned to maintain backward compatibility

4. Repeated fields MUST use packed encoding by default for scalar numeric types.

#### 6.3.2. Message Size Considerations

Implementations SHOULD consider the following size guidelines:

| Scenario | Recommendation |
|----------|----------------|
| Inline blob data | SHOULD NOT exceed max_inline_blob_size_bytes as configured in HydrationConfig |
| Large documents | SHOULD use storage_ref in Blob instead of inline data |
| Vector embeddings | SHOULD use float (32-bit) precision unless double (64-bit) is explicitly required |

#### 6.3.3. Timestamp Encoding

All timestamp fields MUST use google.protobuf.Timestamp:

- Timestamps MUST be encoded in UTC
- The seconds field represents seconds since Unix epoch (1970-01-01T00:00:00Z)
- The nanos field represents sub-second precision (0-999,999,999)

#### 6.3.4. Any Type Encoding

Fields using google.protobuf.Any MUST:

1. Include a type_url that uniquely identifies the message type
2. Contain the serialized message bytes in the value field
3. Use fully qualified type names in the type_url

#### 6.3.5. Schema Reference

The complete Protocol Buffers schema definition is provided in Appendix A. Implementations MUST conform to the schema specified therein.

### 6.4. Entity Lifecycle

#### 6.4.1. Entity Creation

When an entity enters the PipeStream pipeline:

1. The doc_id MUST be assigned according to one of the DocIdDerivationMethod values
2. The ownership context SHOULD be populated if multi-tenancy is enabled
3. At least one data layer SHOULD be populated

#### 6.4.2. Entity Transformation

During pipeline processing:

1. Existing data layers MAY be enriched but SHOULD NOT be destructively modified
2. New data layers MAY be added as processing progresses
3. The parsed_metadata map MUST operate as append-only
4. Processing history MUST be recorded in StreamMetadata

#### 6.4.3. Entity Persistence

Entities MAY be persisted at various points:

1. Inline within PipeStream messages for small documents
2. By reference (DocumentReference) for large documents stored in external repositories
3. The persistence decision SHOULD follow PersistenceConfig settings

### 6.5. Security Considerations

#### 6.5.1. Access Control

Implementations MUST enforce access control based on the OwnershipContext:

1. Documents MUST only be accessible to their owning account
2. Cross-account access MUST be explicitly authorized
3. The account_id field MUST be validated on all operations

#### 6.5.2. Data Integrity

Implementations SHOULD verify data integrity using checksums:

1. Blob checksums SHOULD be validated on read operations
2. Checksum mismatches MUST be reported as errors
3. CHECKSUM_TYPE_SHA256 or stronger SHOULD be used for new content
