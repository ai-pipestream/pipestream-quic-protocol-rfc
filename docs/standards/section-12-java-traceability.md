## Method and status vocabulary

Statements are numbered `S12-001` upward in document order, grouped by the
subsection heading they belong to. Sentences that can only be tested together
are merged into one row; sentences that restate scope with nothing observable
are kept as rows and marked `N/A-JAVA`.

- `COVERED` - at least one assertion fails if the rule is violated.
- `PARTIAL` - exercised on one path, one side, or the happy path only. The
  note says which half is missing.
- `GAP` - no test asserts it. Production code may still enforce it; code
  inspection never earns `COVERED`.
- `N/A-JAVA` - binds a peer role Java does not implement, or is a statement of
  scope with nothing testable. Each is justified in the note.

Two coverage facts apply throughout and are not repeated per row.

1. `RustClientJavaServerTest`, `JavaClientRustServerTest`,
   `RawPeerRustAuthorityTest` and
   `V2CoreClientTest.javaCoreClientNegotiatesAndDetachesFromRustAuthorityWithBothIdentityModes`
   carry `@Tag("sealed-interop")`, which `pom.xml` excludes by default. They
   run only under `-Psealed-interop` with a fresh `cargo build --release` and
   the pinned `4.2.17.Final-pipestream.4` transport. Rows that cite them say
   so; a skipped test cannot by itself earn `COVERED`.
2. `ClientJournalFaultTest` skips entirely as root, and
   `DurableHostIdleWritesTest` skips without `/proc/self/io`.

The split yields 373 statements (S12-001 through S12-373), not the 80 to 120 a
`MUST`-keyword scan suggests, because Section 12 states most of its rules as
declarative fact rather than with a keyword: "Reaching or exceeding either
bound aborts that stream with LIMIT_EXCEEDED", "A repeated or decreasing
identifier is FRAME_ERROR", "Wrong commitment is INTEGRITY_ERROR". Splitting
only on keywords would drop roughly two thirds of the enforceable rules,
including most of the refusal-code taxonomy.

## Clauses where the Java code looks wrong, not merely untested

These are code observations, not test failures. Each names a file and line.

- **D1.** `DurableClient.java:309-326`. The client's idle-control deadline is
  renewed only when a control frame is *received* (`DurableClient.java:1788`),
  never on send and never conditioned on outstanding work, and
  `CoreOptions.defaults()` sets `controlTimeoutMs = 30000`
  (`CoreOptions.java:90`). Section 12.6 allows a wait of up to 30000 ms, and
  `Messages.Watch`/`Messages.Checkpoint` validate `range(waitMs, 0, 30000)`
  (`Messages.java:411`, `:523`). A client that issues the maximum legal wait on
  a conformant server therefore has its own 100 ms ticker fail the connection
  with LIMIT_EXCEEDED at almost exactly the moment the legitimate response is
  due. The server deliberately carves out this case and says so
  (`DurableServer.java:497-509`, `if (!durable() && !outstanding())`); the
  client has no equivalent `outstanding()` guard. No test uses a wait longer
  than 5000 ms, so it is invisible today. Suggested fix: mirror the server's
  carve-out, or renew `lastFrame` on send. **Fixed at ab59dafb**: the
  activity clock is renewed on send, a durable connection with nothing pending
  is never failed for silence, and a pending request is due within the control
  deadline after its own wait (`control response deadline`). Regression:
  `DurableClientControlDeadlineTest`, red on `1e7d25a7`.
- **D2.** `Wire.java:141-147`. The declared-length check runs before the type
  classification, so a private type in 0xC0..0xFF whose body exceeds the
  negotiated control limit is refused LIMIT_EXCEEDED rather than the
  EXTENSION_UNSUPPORTED that 12.1 names for private types without an activated
  profile. "Validate lengths before allocating buffers" justifies the ordering,
  so this may be deliberate, but a peer probing for profile support with a
  large private frame gets a misleading code.
  `V2WireTest.ignorableBodiesAreDiscarded...` only uses a zero-length body. Raised as a
  spec question in handoff section 4, item 7; no code change until answered.
- **D3.** `DurableClient.java:1175-1179`. `DurableClient.checkpoint`
  short-circuits a seal mismatch locally with NOT_READY when the journal's
  verified membership does not match the supplied seal, so the authority's
  INTEGRITY_ERROR at `SessionStore.java:1246` is unreachable through the Java
  client for any scope the journal has verified. The client-side check is
  defensible under 12.8's "the client verifies identity, seal, count partition
  ... before acknowledging coverage", but it means the end-to-end suite has no
  coverage of that server refusal, and the comment at
  `DurableBranchTest.java:166-169` claims server semantics it does not
  exercise. The comment is corrected at the follow-on commit; the code
  question (local refusal allowed, and under which code) is handoff section 4,
  item 8.
- **D4.** `ResultServiceTest.java:110-114` (test defect, not production). The
  `read()` used as evidence that a disk read does not renew the idle deadline
  happens at `nanos == created`, so the assertion cannot distinguish "did not
  renew" from "renewed to the value it already had". The production code is
  correct (`ResultService.java:324-346` never writes `progress`), but S12-276
  is not actually evidenced by that line.

  (before `ce1bfd77`). Installation closed the receiver before the admission
  transaction ran, so for the duration of that transaction the complete
  validated object satisfied the orphan criterion and a concurrent retention
  sweep reclaimed it; the admission then refused NOT_READY for an input the
  peer had fully sent. Found from Meta's C16 `admit-notready` rows, reproduced
  by `InputInstallReclaimRaceTest`, fixed in `ce1bfd77` (installed object pinned
  through the admission transaction; handoff section 5 item 10); store-level
  regression `InputStorePinnedInstallTest`.
- **D11.** `SessionStore` never restarted its write-ahead log; SQLite does so
  only when a writer finds no reader on it, and a continuously polled
  authority never reaches that moment, so the log grew until the file bound
  refused writes (Meta C16a xlarge64 mixed: LIMIT_EXCEEDED `SQLite file
  capacity exhausted` at 1024/256 MiB with the database nearly empty).
  Reproduced by `SessionLogGrowthTest` (six unpaused readers, 100 units,
  12.7 MiB of log), fixed in `4fb8f747` (truncating checkpoint from the
  retention sweep above one sixty-fourth of the bound; `logRestarts` in the
  host status). S12-368 row references the test.
- **D12.** `ReferenceApplications.chunkCopy` admitted every expansion child
  with a fixed 1,000 ms execution duration. A child admitted just before an
  authority restart had its deadline elapse while the process came back, so
  the recovered authority settled it FAILED `execution deadline reached` and
  the STRICT parent failed with it (Kimi driver `g3-restart-same-roots`
  rust-client/java-server on the `28c3369b` jar: child 2:1:3, deadline 13 ms
  before the restarted process could claim it). The Rust reference gives
  children the parent's execution duration. Fixed in `ada67cec`:
  `DurableHost.Production.executionMs` exposes the parent's fixed duration
  and chunk-copy admits children with it;
  `DurableBranchTest.authorityExpandedChunksProduceChildrenAndParentReassembly`
  asserts the inherited duration on every expanded child (red before at
  1,000 ms). S12-175 row references the assertion.

## Gap-closing proposals, grouped by fixture

Each proposal names the smallest stimulus and the assertion that would move a
row to COVERED. They are ordered within each fixture by cost.

### RawDurablePeer against the Java authority

`RawDurablePeer` already exposes `sendBytes(byte[])` (arbitrary control octets,
with the type octet and the length prefix independent of the body),
`sendInput(header, payload, finish)` returning the live `QuicStreamChannel`,
`connection.createStream(...)` for malformed input headers and extra
bidirectional streams, `holdIncoming` for receiver stalls,
`streamCredit()`/`awaitStreamCredit(n)`, and `error(ProtocolError.Code)` for
connection-close code assertions. Every proposal below needs only those.

- **P-PEER-1** (S12-184, the STOP_SENDING half). Admit an input, then resend the
  identical header on a new stream. Capture the returned `QuicStreamChannel`
  and assert the peer observes STOP_SENDING with application error exactly 0.
  This is the only test that would exercise
  `StreamTransport.Data.stopReplayed`.
- **P-PEER-2** (S12-185). Same setup; after the STOP_SENDING, assert the
  client's pending receipt is still outstanding until the correlated
  `AdmissionResponse` arrives.
- **P-PEER-3** (S12-011). Raise the peer's own
  `initialMaxStreamsBidirectional` so the transport permits a second
  bidirectional stream, then assert the server closes FRAME_ERROR from
  `DurableServer.java:462` rather than the peer's transport refusing first.
- **P-PEER-4** (S12-023, D2). Send a private type 0xC0 with a declared body
  within the negotiated control limit and assert EXTENSION_UNSUPPORTED; then
  the same type with an oversized body and pin whichever code the spec intends.
- **P-PEER-5** (S12-028). Send a CAPABILITIES offer with a 33-entry supported
  list, and one with a decreasing list. Assert FRAME_ERROR on the connection.
- **P-PEER-6** (S12-079). DONE at `dce9d384` (`ResultAbortWireTest`). Request a result, let the header be written, then make
  the sender fail mid-payload. Assert the stream is reset and that no second
  control response arrives for that request id.
- **P-PEER-7** (S12-288, S12-289, S12-290). Declare 300 entities across two
  `Declare` batches, then `Page(scope, after, 256)` twice. Assert the first page
  has `more() == true` with exactly 256 increasing ids all greater than
  `after`, the second has the remainder with `more() == false`, and that an
  empty page on an unsealed scope is followed by a successful later
  declaration.
- **P-PEER-8** (S12-265, OUTPUT_UNAVAILABLE over the wire). Publish a result,
  delete the installed object file, then `Read`. Assert a correlated REFUSAL
  with OUTPUT_UNAVAILABLE and that the work view is still SUCCEEDED.
- **P-PEER-9** (S12-277, new reads after revocation). Revoke the session, then
  send a fresh `Read`. Assert UNAUTHORIZED and that `ResultService.usage()` did

- **P-PEER-10** (S12-056). DONE: the existing ceiling test already asserts transport error 0x02 on a non-application close. Fill the connection ceiling and attempt one more QUIC

- **P-PEER-11** (S12-072). Send a REFUSAL-shaped frame carrying code 19 and

### RawDurableAuthority against the Java client

`RawDurableAuthority` can already forge every `v2-result-header` field, write
arbitrary bytes and length prefixes on a result stream, open duplicate or
unsolicited unidirectional streams, and it records every frame the client sent
in `received`. It cannot yet forge CAPABILITIES or answer non-result control
requests; the two proposals that need a hook say so.

- **P-AUTH-1** (S12-078). DONE at `dce9d384`. On a contradicting header, after the client aborts,
  assert `received` contains no client-to-server `Refusal` at all. No new hook
  is needed; this is a negative assertion over an existing queue.
- **P-AUTH-2** (S12-292, S12-293, S12-294, S12-295). Answer `Page` and `Watch`
  with a contradictory parent/child combination: a child scope whose `parent`
  work key names an entity absent from the parent's verified sealed membership.
  Assert the client raises INTEGRITY_ERROR, that its journal still holds the
  prior validated commitment, and that a later checkpoint refuses to
  acknowledge coverage. Needs a control-script hook in
  `RawDurableAuthority.Control.handle` so `Page` and `Watch` do not fall to the
  `default -> Refusal(NOT_FOUND)` arm.
- **P-AUTH-3** (S12-037, S12-030, S12-028 from the client side). Add a
  CAPABILITIES hook so the fixture can send an unsolicited selection, an
  increased limit, a version-1 profile id and a second CAPABILITIES. Assert
  FRAME_ERROR on `client.ready()` for each. Today only `V2CoreClientTest`'s
  hand-written `MaliciousServer` can do this, and only for two of the four.
- **P-AUTH-4** (S12-280, S12-283). Answer `GetManifest` with a manifest whose
  output locator names a different authority host and port. Assert the client
  never opens a connection to it and never sends credentials there; `received`
  plus a listener on that port is enough.

### Cross-language (sealed-interop)

The interop suite proves only three refusal codes across the language boundary
(INTEGRITY_ERROR from Rust to a raw Java peer, CONFLICT from Rust to the Java
client, and a string-matched APPLICATION_UNSUPPORTED from Java to the Rust
client), and only the DECLARED to ACTIVE to SUCCEEDED path. Every interop
admission is mode 0, even though the Rust CLI exposes `--mode` and the Rust
authority registers `reassemble/v2` and `chunk-copy/v2`.

- **P-INTEROP-1** (S12-096 against Rust). Remove one fingerprint from the
  principal-map TSV before `v2 serve` so the Rust authority sees a trusted but
  unmapped client, then assert the Java peer's connection closes UNAUTHORIZED
  with no capabilities response. Today
  `RustClientJavaServerTest.rustClientWithUnmappedIdentity...` uses a foreign CA
  and asserts only a nonzero exit code, so the clause its name claims is
  untested.
- **P-INTEROP-2** (S12-163, S12-167 against Rust). Run one `--mode 1` and one
  `--mode 2` admission through the Rust CLI against the Java authority, and one
  in the other direction. Assert the child scope producer is 0 and 1
  respectively and that the parent reassembles.
- **P-INTEROP-3** (S12-118 against Rust). Point `RawDurablePeer.sendInput` at
  the Rust authority with a producer-1 work key and assert UNAUTHORIZED. One
  line, since the harness already accepts any work key.
- **P-INTEROP-4** (S12-202, S12-215 against Rust). Use the unused Rust CLI verbs
  `retry`, `cancel`, `skip` and `cancel-scope` against the Java authority and
  assert the exact refusal codes and terminal states. FAILED, CANCELLED and
  SKIPPED are currently never observed across the language boundary.
- **P-INTEROP-5** (S12-350 against Rust). Start the Rust authority without
  `--trust-system-clock`, or with a skewed clock, and assert CLOCK_UNSAFE
  reaches the Java client.
- **P-INTEROP-6** (Section 12.9 crash boundaries). `RustAuthorityProcess.close()`
  asserts a clean SIGTERM drain, so no interop test can reach them. Add a
  `kill()` that sends SIGKILL without the drain assertion, then assert the Java
  client's replay of the same operation identity returns the identical receipt
  after the Rust authority restarts.
