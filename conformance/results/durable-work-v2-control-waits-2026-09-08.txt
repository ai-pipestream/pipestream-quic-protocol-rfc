Implementation scope
  Java SessionStore.checkpoint distinguishes a matching sealed scope without
  closure from an unsealed/mismatching/unauthorized scope. It verifies closure
  and response bounds in the authorized snapshot, without a UTC lease.
  ControlWaitService runs observations on bounded dedicated workers. A shared
  service enforces finite pending/per-owner capacity across connections and
  sessions, without keeping a database worker between polls. Each observation
  rechecks current authorization. Abandoning a handle never cancels durable
  execution; a queued/running read stays charged until the worker returns.
  WORK expiry returns a current unchanged view; checkpoint expiry is WAIT_TIMEOUT.
  Positive checkpoint waits include queue time and cannot return late success.
  Zero wait may return an already committed closure. The same positive-wait
  deadline guard was corrected in Rust and clarified in Section 12.

Scope limits
  These observations are not a Java durable endpoint. The host must share one
  service across its authority connections; separate instances/processes do not
  coordinate these volatile limits. The transport still owns correlation,
  connection-local pending limits, delivery deadlines, input/result transfers
  and drain accounting. No Java durable profile advertisement is added.
  Queue/thread/record bounds are not a whole-process RSS measurement or a hard
  storage-latency guarantee. Existing closure verification retains its streaming
  audit costs. No neutral two-direction durable failure-driver or equivalent
  workload/gRPC comparison acceptance is claimed. Those goal deliverables remain
  mandatory, along with full Java durable server/client integration.
  No hosted-CI, main-merge, deployment or IETF-submission claim is made.
