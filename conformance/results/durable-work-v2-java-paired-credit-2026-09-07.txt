replenishment and maximum connection windows. A 39-byte native caller send
buffer separates stream and connection credit. Original ACK/stream-credit
packets are delivered; original MAX_DATA packets are withheld. Copies alone are
decrypted for inspection. No frames are repacketized and no fake ACKs are used.

The sender consumes all 512 initial connection-credit bytes with one control

Changes and boundaries
----------------------
- Opt-in Config::set_pair_receive_credit / QuicCodecBuilder.pairReceiveCredit.
  Default false; enabled by Java V2 StreamTransport.
- MAX_DATA is paired with MAX_STREAM_DATA and MAX_STREAMS in each packet.
  Insufficient packet space leaves stream credit pending. One sufficient
  MAX_DATA can cover several updates in that packet; previously advertised
  connection limits are not reduced.
- Connection autotuning and stream-driven lower bounds remain applicable.
- Per-direction MAX_STREAMS loss state persists until emission. Superseded
  lost limits do not reschedule older credit. This recovery correction is
  independent of the optional pairing policy.
- Modified transport coordinates advance to 4.2.17.Final-pipestream.3.
- Section 12.1 explicitly covers peer-observable packet loss/reordering and
  retransmitted/replacement credit. It permits equivalent reservation policies,
  not only this implementation's packetization strategy.
